# Interrupted HTTP reads and deadline validation

Issues [#140](https://github.com/bin9208/openpilot-rust/issues/140) and [#141](https://github.com/bin9208/openpilot-rust/issues/141); full runtime [#1](https://github.com/bin9208/openpilot-rust/issues/1).

Post-merge support validation at `3e87a2ee21d75beb9f0519fe51885ce74bd95a38` captured `EINTR` while the native uploader read a PUT response. The failed attempt caused another complete HTTP upload. [The failed job](https://github.com/bin9208/openpilot-rust/actions/runs/36812380849/job/110210052371) retained the failure and duplicate requests in [artifact 11139867655](https://github.com/bin9208/openpilot-rust/actions/runs/36812380849/artifacts/11139867655).

The pinned ureq TCP transport propagates an interrupted `TcpStream::read`. `openpilot-http-transport` now retries only interrupted input reads with the remaining duration of the original socket deadline. It never restarts the HTTP request or resets that deadline. Other errors propagate and bytes returned after the deadline are still rejected. Python retries interrupted socket operations too; see [the Python socket contract](https://docs.python.org/3/library/socket.html#socket.socket.recv). Output handling is unchanged: the pinned TCP transport uses `write_all`, which already handles interrupted writes while preserving partial progress.

The regression first failed against the old wrapper with `Io(Kind(Interrupted))`, then passed after the fix. Four transport checks cover interruption with a decreasing deadline, expiration during interruption, non-interrupted error propagation and late-byte rejection. An owned LD_PRELOAD fixture injects two `EINTR` results at actual loopback PUT response reads. Before the fix, the actual uploader emitted four PUTs for two files and the existing strict daemon assertion failed. The fixture records each injection and requires exactly two GETs/two PUTs after the fix, both upload markers, two success records and clean shutdown. It does not intercept vehicle or external traffic.

The separate [deadline failure](https://github.com/bin9208/openpilot-rust/actions/runs/36813036020/job/110212050805) came from an invalid test timing assumption: a server receiving a request does not establish the client's socket-read start. The original Python source succeeded despite the server waiting 10.05 seconds. A controlled reproduction inserted 150 ms scheduling delay before the source's actual read with a 100 ms socket timeout; a response sent after 180 ms still succeeded because the read itself waited only about 30 ms. This demonstrates the fixture error without changing the source policy.

The loopback late/stall scenarios now delay 11/12 seconds against the unchanged ten-second runtime timeout, avoiding the former 50 ms scheduling margin. All ten source/native scenarios and their success/failure, xattr and exact request comparisons remain mandatory. The progressing-body cases still take eleven seconds in total with individual gaps below ten seconds. Precise late-byte rejection is separately covered at the transport boundary; the end-to-end oracle is not presented as a 50 ms deadline measurement.

The fixed actual uploader passes with exactly two GETs/two PUTs, two injected read interruptions, both upload markers and exit zero. The normal six daemon scenarios and three startup failures also pass. All ten source/native deadline scenarios (20 executions), 212 filesystem cases, 10,000 backoff decisions and 32 HTTP comparisons pass; compressed request bytes remain exact. Focused Clippy, Ruff and 13 workflow-policy tests pass.

Evidence is preserved in `.analysis/scratch/2026-10-01-rust-http-eintr/`: `test-{red,green}.log`, `http-{red,green}/`, `daemon-green/`, `deadlines-green/`, `reference-green/` and `deadline-origin-repro.{py,json}`. CI retains the actual uploader regression under `rust-support-runtime-evidence`. No production timeout, upload policy, process selection or device setting changes. No vehicle access or device performance claim.
