# openpilot-rust: 전체 런타임 Rust 포팅 설계안

작성: 2026-09-29. 상태: 사용자 진행 승인; M0 구현 중, 실기 성능 검증 전.

## 목표와 사용자의 요구

Snapdragon 845 기반 장치에서 기존 포크의 기능과 차량 동작을 유지하며 프로젝트가 소유한 런타임을 Rust로 전환한다. 목적은 CPU 시간, 발열, 주기 초과를 줄이고 추가 모델을 실행할 여유를 만드는 것이다. 기존 bin9208/openpilot 및 D:\Openpilot의 진행 중 작업과 분리한다. 부분 포팅만으로 전체 완료라고 선언하지 않는다.

추가 모델 예시는 YOLO26n 10Hz이며 사용자가 제시한 52ms는 검증되지 않은 참고값이다. 입력 크기, 정밀도, 실행 장치, 전/후처리 포함 범위를 확인하기 전 성능 계약이나 달성 증거로 쓰지 않는다. 이 포팅 단계에서 새 모델을 기존 차량 제어에 연결하지 않는다.

## 출발점과 저장소 분리

- 기준 저장소: https://github.com/bin9208/openpilot, 공개 저장소.
- 고정 기준: dev의 f3a92524d87be714f6b8b5f44ecdc8319a8c53d1. 조회 시 fast checks, integration gate, check mapped user docs 성공. 별도 sync 검사 실패는 기존 기준점의 알려진 상태로 기록한다.
- 기존 로컬 c3-c4-bin9208-wip 및 미커밋 변경은 복사/커밋/수정하지 않는다. 변경 이식이 필요하면 원본 작업의 병합 이후 별도 이슈로 가져온다.
- 제안: bin9208/openpilot-rust 독립 저장소에 공개 원본의 Git 이력과 라이선스를 유지한다. GitHub 정식 추가 포크가 필요하면 별도 소유자를 지정한다. 기존 포크를 삭제하거나 fork network에서 분리하지 않는다.
- 새 저장소는 원본과 같은 공개 범위를 제안한다. 개인 로그, 자격증명, NAS 경로에 담긴 원본 데이터, 로컬 미추적 파일은 업로드하지 않는다.
- 로컬 체크아웃은 D:\Openpilot-Rust처럼 별도 디렉터리를 사용한다. 원본과 .git을 공유하지 않는 독립 clone이며 디렉터리 쓰기 권한을 확인한다.
- 새 저장소 origin만 쓰기 대상으로 삼고 source remote는 읽기 전용으로 취급한다. 원본에 PR/이슈/푸시를 만들지 않는다.
- dev는 통합, main은 릴리스. 초기 기준점 생성 이후 변경은 이슈 브랜치 -> dev PR. 기존 원격의 자동 동기화/배포/NAS/Wiki 작업은 새 저장소에서 자동 실행되지 않도록 점검 후 필요한 CI만 활성화한다.

## 선택할 접근법

1. 권장: 최종 범위는 전체 포팅으로 유지하되 프로세스별 Rust 대체 구현을 만들고 원본과 동일 입력으로 검증한다. 이행 중 혼합 실행은 임시 상태이며 완료 기준이 아니다.
2. 일괄 재작성: 한 번에 전체 스택을 바꾼다. 런타임 의존성은 일찍 제거할 수 있지만 동작 차이와 성능 회귀의 원인을 분리하기 어려워 권장하지 않는다.
3. Python 병목만 영구적으로 부분 이식: 투자 대비 성능에는 유리할 수 있지만 사용자가 요청한 전체 포팅 목표와 달라 이번 최종 목표로 선택하지 않는다.

## 전체의 범위와 외부 의존성 경계

전환 대상은 프로세스 관리자, 공통 런타임, 로그/계측, 내비/웹 서버, 위치 추정, 레이더, 주행 계획, 차량 인터페이스, 제어/상태 관리, UI 및 모델 실행 제어를 포함하는 프로젝트 소유 코드다. 기존 프로젝트 소유 C/C++ 서비스도 포팅 목록에서 제외하지 않고 후반 단계에 검증한다.

Linux/AGNOS 커널과 드라이버, GPU 펌웨어, 모델 가중치, acados, raylib, 코덱 등 외부 라이브러리는 그 자체의 Rust 재작성을 기본 범위로 삼지 않는다. 필요한 네이티브 API는 작은 FFI 경계로 격리하고 수명/스레드/버퍼 소유권 계약을 검증한다. C 라이브러리를 호출한다고 Rust 포팅 실패로 보지는 않지만 Python 런타임을 숨겨 호출하는 구성은 최종 런타임 전환 완료가 아니다.

모델 실행 경로는 가장 큰 기술적 검증 항목이다. Python tinygrad를 단순히 감싼 것은 완전 전환이 아니다. 현 모델의 QCOM 실행 커널/그래프, VisionIPC 버퍼, 동기화 및 수치 결과를 Rust 실행부에서 재현 가능한지 선행 검증하고 별도 이슈로 추적한다. 가능하다는 가정만으로 완료를 약속하지 않는다.

빌드 시 모델 변환/테스트 oracle에 Python을 남길 수 있으나 실행 시 의존 여부와 명확히 구분한다. 웹 브라우저 JS 및 Android 애플리케이션의 플랫폼 언어는 기기 CPU 런타임 전환 범위와 별도로 기록한다. Panda 안전 펌웨어의 독립 보호 기능은 이 프로젝트의 언어 변경과 함께 제거하거나 완화하지 않는다.

## 호환성과 실행 구조

- 메시지 이름, Cap'n Proto schema ID/ordinal, 단위, validity, monotonic timestamp 의미를 보존한다. wire encoding만 같다고 msgq/VisionIPC 호환이라고 보지 않는다.
- msgq 공유 메모리 전송 및 VisionIPC의 버퍼 수명, 최신 프레임 선택, 큐 정체/드롭, 재접속을 검증한다. 초기 FFI 뒤에 Rust 소유 API를 둔다.
- Params의 저장 형식, 기본값, 차량별 설정, 상태 전이, 지원 차량 목록을 보존한다.
- 첫 비교에서는 100Hz 제어/20Hz 모델 등 기존 주기, 코어 affinity, priority를 유지한다. 스케줄링 변경과 언어 변경을 하나의 성능 결과에 섞지 않는다.
- 안전 관련 상태와 CAN 출력의 동등성을 필수 검증한다. 부동소수 계산은 모듈별 오차 허용값을 포팅 전에 정하고, 그 결과가 다른 상태 분기나 안전 제한 위반을 유발하면 실패다.
- shadow 프로세스는 실제 CAN 송신 권한이나 동일 topic의 publish 권한을 갖지 않는다. 실제 교체는 한 프로세스씩 선택할 수 있어야 한다.
- 고빈도 루프는 사전 할당, bounded queue, 명시적 소유권을 우선한다. Rust라는 이유만으로 무할당/무복사/실시간성을 주장하지 않는다.

## 단계별 작업과 완료 증거

### M0. 별도 저장소, 빌드 및 기준 측정

GitHub 이슈를 먼저 만들고 고정 SHA/프로세스 목록/런타임 언어/외부 의존성을 manifest로 기록한다. Cargo workspace, 잠금된 toolchain, x86_64 Linux 테스트, aarch64 대상 빌드를 구성한다. 현재 procLog 활성화 상태와 실제 메시지 기록을 확인하고 측정 도구 자체의 부하를 별도 비교한다.

첫 코드 포팅은 공통 시간/필터 등의 작고 동등성 검증 가능한 모듈과 Linux 프로세스 CPU 시간 파서로 제한한다. 이는 기반 구현이며 차량 제어 Rust 전환이나 CPU 절감 달성으로 표현하지 않는다. Windows 빌드만 성공한 것으로 AGNOS 실행을 주장하지 않는다.

### M1. IPC와 독립 프로세스

Cap'n Proto/msgq/Params 경계를 검증하고 Rust procLog 생산자를 기존 메시지 소비자에 연결한다. 누락 PID, PID 재사용, /proc 읽기 경쟁, 재시작, 메시지/메모리 누수 및 기록 주기를 테스트한다. 기존 proclogd와 동시에 같은 topic에 publish하지 않는다.

### M2. 모델 실행 경로 선행 검증

Rust에서 기존 모델 실행 가능성을 조기에 검증한다. 동일 모델/입력의 결과 오차, 전처리, GPU/CPU 동기화, 버퍼 수명, warm-up/정상/장시간 상태를 비교한다. 이 경로가 불가능하거나 외부 런타임이 필요하면 전체 전환 제약을 명시하고 계획을 수정한다.

### M3. 내비·지원 서비스·UI

내비 수신/속도 선택, 웹/통신, 로그/하드웨어 관리, 화면을 서비스별로 전환한다. 기존 한/영 문서 매핑과 회귀 테스트를 유지한다. 사용자 설정이나 제어 정책을 성능 개선 명목으로 바꾸지 않는다.

### M4. 추정·레이더·계획

위치/보정/차량 파라미터 추정, 레이더 경로, longitudinal/lateral 계획을 동일 로그 및 명시적인 edge case로 비교한다. acados 등 native solver는 우선 동일 버전을 사용해 언어 효과와 solver 변경 효과를 분리한다.

### M5. 차량 인터페이스·제어·상태 관리자

차량별 CAN 인코딩/디코딩, 100Hz 제어, 상태 및 이벤트 처리, manager 전환을 독립 이슈로 진행한다. 최초 IONIQ 5 PE 검증은 전체 지원 차량 검증으로 간주하지 않는다. 버스 오류/센서 stale/재시작/비정상 입력에 기존 안전 반응을 유지한다.

### M6. 프로젝트 소유 네이티브 서비스 및 최종 런타임

카메라/인코더/기타 프로젝트 소유 C/C++ 서비스의 Rust 소유 코드를 검증한다. 외부 드라이버/코덱 FFI 의존성은 명시한다. 원본 Python 실행 경로가 남은 모듈을 manifest에서 확인하고 최종 기기 실행 경로에서 제거한다. 미전환 항목이 있으면 전체 완료라고 하지 않는다.

## 성능/기능 합격 기준

- 같은 장치, 모델, 해상도, 활성 기능, 입력, 주기, 냉각/전원 조건에서 baseline과 Rust를 비교한다. 옛 로그는 참고이며 새 baseline을 대체하지 않는다.
- 코어/프로세스별 CPU 시간, 메모리, 주기 초과율, p50/p95/p99 실행/대기/종단 지연, 프레임 드롭, 실제 클럭, 온도/전력을 측정한다.
- 최소 30분 부하 및 열 안정 상태를 포함해 반복 비교하고 측정 변동을 함께 보고한다. CPU/발열이 줄지 않았으면 포팅 성공과 최적화 성공을 구분한다. 근거 없는 절감 %는 목표 달성으로 기록하지 않는다.
- 추가 YOLO 10Hz 실험은 입력 크기/정밀도/백엔드/전후처리 범위를 고정한다. 기존 제어/모델 주기 회귀 없이 지속 처리율 >=10Hz, stale frame을 무한 대기열에 쌓지 않음, deadline 초과와 frame age를 모두 기록한다. 52ms 평균 한 번만으로 성공 처리하지 않는다.
- static/unit 성공, host 실행, aarch64 빌드, 실제 AGNOS 실행, 실차 수용을 별도 상태로 관리한다. 실기 조건 미충족 이슈는 열어 둔다.

## CI와 변경 통제

이슈별 독립 브랜치, 빠른 push 검사, PR 빌드/통합 검사, 병합 후 검사를 새 저장소에 적용한다. Cargo fmt/clippy/test, 참조 구현 동등성 검사, aarch64 빌드, 기존 회귀/한영 문서 검사를 구분한다. host cross-build를 target runtime 테스트로 표시하지 않는다.

기존 fork에서 복사된 자동 동기화가 Rust 변경을 덮어쓰거나 원본 Wiki/NAS에 배포하지 않도록 새 저장소의 workflow를 별도 설계한다. 라이선스/저작권, source SHA와 의존성 버전은 보존한다. 실제 required checks와 branch protection 적용 여부를 조회하고 빈 required gate를 성공 처리하지 않는다.

## 사용자 검토 사항

1. 저장소 분리 방식: 기존 개인 포크를 유지하는 독립 openpilot-rust vs 별도 소유자의 정식 GitHub 포크.
2. 이 설계의 전체 범위: 프로젝트 소유 런타임은 최종 Rust 전환, 커널/드라이버/외부 라이브러리의 FFI 사용 허용.
3. 검증 가능한 단계별 전체 전환과 원본 동작 유지. 개선량은 실기 검증 전 미확정.

사용자가 진행 및 기존 포크에 영향 없는 작업의 자율 실행을 승인했다. M0 실행 계획은 m0-plan.md이며 아직 미구현인 전체 런타임 단계는 계속 열린 상태로 추적한다.
